## Provider contract and rationale

Reactor's [FastH3 API](https://www.reactor.inc/models/fast-h3/api) documents model `reactor/fast-h3`: enqueue a prompt, wait for `clip_generated`, then explicitly play its clip ID over the video track. Generation and playback are separate. Image seeding and continuity are optional; Reverse Prompt omits them. The model supports a 1344×768 landscape canvas at 24 fps. Its [clip geometry source](https://github.com/reactor-team/infinite-livestream/blob/main/fast-h3/fasth3_clip_plan.py) maps the published minimum 5.167 seconds to 124 frames. The API streams a prepared clip; it does not return a downloadable MP4.

The [model listing](https://www.reactor.inc/models/fast-h3/info) currently advertises $0.42 per active minute. [Billing](https://docs.reactor.inc/resources/billing) uses session ready time, including idle time. A five-second output does not establish a five-second bill. Advertised generation speed is not measured end-to-end demo latency.

The installed Python SDK 1.5.1 has `send_command` with correlated `{type,data}` replies, model-message callbacks on the event loop, and immutable BGRA raw-frame callbacks on a delivery thread. No additional dependency, model download, provider account or model-selector environment variable is introduced. The cloud model is fixed in the game provider; the local MiniLM scorer stays pinned separately.

## Implemented sequence

1. Atomically consume one existing campaign attempt and set the unresolved marker before any Reactor traffic. Mint a token for FastH3 only, one session, maximum duration 90 seconds. Every accepted relay prompt opens its own session.
2. Confirm autoplay off, landscape canvas and end-of-clip flush on. Enqueue only the accepted current text plus the existing fixed rendering instruction, requested 5.167 seconds and opaque attempt metadata. Require a correlated clip acknowledgment and matching generation-complete event. Validate124 source frames from completion, the preserved acknowledgment, or one bounded read of that exact clip in `get_queue`. Compact messages and whole-number JSON floats are accepted; invalid or mismatched metadata fails. Never retry an ambiguous enqueue.
3. Play that specific clip. Capture begins only after its matching `clip_started` event. Ignore idle frames before that event and duplicate start messages. A different clip, rejected generation, unconfirmed setting or malformed required message ends unscored.
4. Encode the first 120 received frames as a five-second silent H.264/yuv420p MP4. Validate exact provider dimensions 1344×768, payloads and available timestamp order/span. The bounded queue holds at most 16 frames (about 63 MiB of pixel bytes). Overflow fails instead of dropping frames. A playback-end event before 120 frames rejects the clip and prevents idle padding.
5. Cancel and await all owned command/capture tasks and FFmpeg on failure/reset. Independently confirm CLOSED/INACTIVE or 404 for the same provider session before clearing the guard and publishing validated media. A session-ID mismatch is not terminal evidence. Failed output is deleted; quota is never refunded. An uncertain session blocks reset completion, closure, switching and future live attempts after restart.

The application deadline remains 90 seconds. Cleanup remains owned when that deadline expires. The operator spike reports model, consumed attempt, startup/generation/total elapsed time, declared source frames, captured/encoded frames, dimensions, bytes and confirmed closure without player text or credentials. No provider recording service is used.
