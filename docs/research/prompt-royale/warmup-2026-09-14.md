# Helios extended startup check — 14 September 2026

Increasing the startup allowance to five minutes did not produce a connectable
Helios session. The final attempt stayed at REST status `CREATED` through 34
readiness checks, received no frames, and was independently confirmed closed.
This establishes that startup did not finish within five minutes; it does not
establish whether the provider was queuing for capacity or failing to start a runtime.

## What the statuses mean

[Reactor's session guide](https://docs.reactor.inc/concepts/sessions) describes
SDK connection states: `disconnected` has no connection, `connecting` negotiates
session creation, `waiting` waits for GPU assignment, and `ready` permits commands
and media. The [FAQ](https://docs.reactor.inc/resources/faq) says assignment usually
takes seconds, extended waiting typically indicates model capacity saturation,
and unusually long waits should be reported to support@reactor.inc with the session ID.

REST status `CREATED` is separate from those SDK connection states. The
[official SDK protocol implementation](https://github.com/reactor-team/reactor-client-sdks/blob/9156ce9b09b3ebb8ed717d49d8ac69c5e44cec1d/crates/reactor-protocol/src/session.rs)
considers a session connectable only after both `capabilities` and
`selected_transport` are populated. That readiness condition never became true
in the five-minute attempt. No generation command was sent.

## Attempts

Both attempts used one session creation, without creation retries or concurrent
game sessions. Neither received an HTTP 429. Both sessions were confirmed closed,
and the unresolved-provider journal was cleared by normal verified cleanup.

| Attempt | Observed result | Elapsed including cleanup | Frames received |
| --- | --- | ---: | ---: |
| Extend the outer startup timeout to 300 seconds | Native SDK stopped with `REQUEST_TIMEOUT` while waiting | 163.802 seconds | 0 |
| Create once through REST, poll for up to 300 seconds, then adopt with SDK if ready | 34 checks remained `CREATED`; startup allowance expired | 302.077 seconds | 0 |

The first attempt revealed a second timeout: the native SDK limits session-readiness
polling to 20 attempts with exponential delays capped at ten seconds. Extending the
outer timeout alone could not extend that internal limit. The final experiment
therefore polled the same session through REST until our own deadline, matching the
SDK's readiness condition. SDK adoption would reuse that session without creating
another one, as described in the session guide.

The REST experiment can be reproduced with `--startup-timeout 300 --startup-mode rest`,
with a 360-second session cap and a 480-second token lifetime. It allows 60 seconds for capture after
connection readiness and reports progress every 15 seconds. This experimental
override does not change the normal game's 180-second round deadline or its default
60-second capture lifecycle. The owner explicitly terminates adopted sessions and
independently checks closure, including on timeout.
